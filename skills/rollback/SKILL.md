# /rollback — ย้อน production กลับ

> เรียกด้วย `/rollback` เท่านั้น — ห้าม auto-trigger เด็ดขาด
> การย้อน production เป็นการกระทำที่กระทบผู้ใช้จริง ต้องมาจากคำสั่งของพี่ A เท่านั้น

**อ่าน `vibe-coding-quality/references/rollback-runbook.md` ให้จบก่อนเริ่มทุกครั้ง**

## ลำดับการทำงาน

1. **ถามอาการก่อน** แล้วใช้ตารางตัดสินใจข้อ 0 ของ runbook
   - ตัวเลข/การคำนวณผิด → ย้อนทันที (เครื่องมือโรงงานที่ให้ค่าผิด อันตรายกว่าที่ล่ม)
   - หน้าตาเพี้ยนแต่ใช้งานได้ → เสนอให้แก้ไปข้างหน้าแทน ไม่ต้องย้อน
2. **เช็คก่อนว่าเวอร์ชันที่จะย้อนไป bump `DB_VERSION` หรือเปล่า**
   → ถ้า deploy ที่พังเปลี่ยน `DB_VERSION` ไปแล้ว **ห้ามย้อน** (ข้อ 5 ของ runbook —
   เบราว์เซอร์ปฏิเสธการเปิด DB ด้วย version ที่ต่ำกว่าที่มีอยู่ แอปเก่าจะเปิดไม่ขึ้นเลย)
   ต้องแก้ไปข้างหน้าแทน · **ตรวจข้อนี้ก่อนรันคำสั่งใดๆ**
3. `wrangler deployments list` → แสดงรายการให้พี่ A **ยืนยันว่าจะย้อนไปเวอร์ชันไหน**
   ห้ามเลือกเอง
4. รัน rollback
5. `git revert` + push ให้ git ตรงกับ production — **เช็ค stack ก่อนว่าต้อง bump `CACHE_NAME` ไหม**
   (`grep -r CACHE_NAME` ในซอร์สจริงของแอปนั้น ไม่เดาจากชื่อ stack):
   - **Single HTML File (มี `sw.js` เขียนมือ + `CACHE_NAME`):** bump `CACHE_NAME` เดินหน้า
     (v7 → v8) ด้วย — ข้อนี้ห้ามข้าม ไม่งั้น rollback จะ "สำเร็จ" แต่ผู้ใช้ยังเห็นของพัง (ข้อ 3.1 ของ runbook)
   - **Multi-File (`vite-plugin-pwa` สร้าง service worker ให้เอง ไม่มี `CACHE_NAME`):** ไม่ต้อง bump
     แต่ให้ตรวจบนมือถือ 1 เครื่องที่เคยเปิดเวอร์ชันพังไว้ว่าได้ของที่ย้อนแล้วจริง (ข้อ 3.2 ของ runbook)
6. เปิด URL จริง เช็ค build stamp ว่าเป็นเวอร์ชันที่ตั้งใจ
7. **เปิด GitHub issue** บันทึกว่าเกิดอะไร และทำไมเทสต์ไม่จับ
8. เสนอเทสต์ที่จะแดงถ้าบักนี้กลับมา — rollback ที่ไม่ตามด้วยเทสต์ คือการเลื่อนปัญหาออกไป

## กติกา

- **ทุกคำสั่งที่กระทบ production ต้องให้พี่ A ยืนยันก่อนรัน** แสดงคำสั่งเต็มให้ดูก่อนเสมอ
- **ห้าม `git reset --hard` + force-push** — `sa-git-manager` ห้ามไว้ และจะทำให้ sync 2 เครื่องพัง
- ถ้ายังไม่เคยซ้อม rollback กับแอปนี้มาก่อน ให้บอกพี่ A ตรงๆ ว่านี่เป็นครั้งแรก
  และคำสั่ง `wrangler` ใน runbook ยังไม่ได้ยืนยันกับเครื่องจริง
