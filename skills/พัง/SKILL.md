# /พัง — Debug Mode

> เรียกด้วย `/พัง` เท่านั้น — skill นี้ตั้ง `disable-model-invocation: true` เพราะคำว่า "พัง"
> กำกวมเกินไปสำหรับให้ Claude ตัดสินใจ auto-trigger เอง (พี่ A ทำงานโรงงาน PTA มีโอกาสพิมพ์ประโยค
> เช่น "เมื่อวานเครื่อง Boiler พังที่หน้างาน" ซึ่งไม่เกี่ยวกับโค้ดเลย) — ต้องพิมพ์ `/พัง` ตรงๆ
> เท่านั้นถึงจะเข้าโหมดนี้

เมื่อถูกเรียก ให้ Claude เข้า Debug Mode ทำตามลำดับนี้เสมอ — อย่าข้ามขั้นตอนแม้พี่ A จะรีบ
เพราะข้อมูลไม่ครบ = วิเคราะห์ผิดจุด = เสียเวลามากขึ้น:

```
1. ถาม: "Error message คืออะไรคะ?"
2. ถาม: "เกิดขึ้นตอนไหน? (คลิกอะไร / หน้าไหน / ทำอะไรอยู่ก่อนพัง)"
3. วิเคราะห์ Root Cause
   - ถ้าโปรเจกต์ใช้ vibe-coding-core pattern (9-module: IIFE ใน Single HTML File / ES module คนละไฟล์ใน Multi-File) ให้ระบุ Error Type
     ตาม Error Taxonomy ใน vibe-coding-core/references/error-handling-and-data.md
   - ใช้ Five Whys ถ้า root cause ไม่ชัดเจนตั้งแต่รอบแรก
4. เสนอ Fix พร้อมอธิบาย WHY — ทำไมบั๊กนี้ถึงเกิด ไม่ใช่แค่ "แก้บรรทัดนี้"
5. หลังแก้เสร็จ: บอกวิธี verify ว่าหายแล้วจริง (เช่น "ลองทำ [ขั้นตอน] อีกครั้งดูนะคะ")
```

**กฎ:** ถ้าแก้ไปแล้ว 3 รอบยังไม่หาย ให้หยุดแล้วสรุปให้พี่ A ฟังตรงๆ ว่าลองอะไรไปแล้วบ้าง แทนที่จะวนแก้ไปเรื่อยๆ แบบเดา
