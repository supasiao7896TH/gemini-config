# dev-skills-roadmap.md

สมุดจด roadmap การเรียนรู้พื้นฐานการเขียนโค้ด — เริ่มจากมือใหม่เกือบศูนย์ ค่อยๆ ไต่ไปถึงระดับ senior dev เก็บไว้อ่านย้อนหลัง/ทบทวนหากลืมเนื้อหา

**เริ่มเมื่อ:** 2026-08-12 (session แรกในโปรเจกต์ `Check Out of Range Log`)

**Baseline ตอนเริ่ม:** เขียนโค้ดเองแทบไม่เป็นเลย (ไม่รู้ syntax พื้นฐานภาษาไหนเลย) แม้จะสั่ง AI เขียนแทนแบบ Vibe Coding มานานแล้ว

**โหมดการเรียน — ปรับใหม่ 2026-08-12 (วันเดียวกับที่เริ่ม):** ทดลอง format "ให้โจทย์ฝึกเขียนเอง" ไปครั้งแรก (โจทย์ `myName` variable) แล้วพี่ A **ปฏิเสธทันที** — เหตุผล: สุดท้ายก็จะใช้ Vibe Coding (ให้ AI เขียนแทน) อยู่ดี ไม่อยากเขียนโค้ดเอง สิ่งที่ต้องการจริงคือ **เข้าใจ concept** ว่า AI กำลังทำอะไร ทำไมทำแบบนี้ ทำถูกไหม — เพื่อจะได้ไม่กด "OK/อนุมัติ" แบบไม่รู้อะไรเลย ต้องการเรียนไปพร้อมๆ กับตอนที่ AI กำลังเขียนโค้ดจริงให้ (explain-while-doing) ไม่ใช่ sandbox exercise แยกต่างหาก

→ **โหมดที่ใช้จริงตอนนี้:** ไม่มีโจทย์/แบบฝึกหัดอีกต่อไป Claude จะแทรกคำอธิบายสั้นๆ ระหว่างที่เขียน/แก้โค้ดให้ในงานจริง ว่ากำลังทำอะไร ทำไมเลือกวิธีนี้ มี trade-off อะไร เพื่อให้พี่ A ตามทันและประเมินได้

**เนื้อหาผูกกับ:** ทั้งทฤษฎีทั่วไป (JS/Git/HTTP fundamentals) และโค้ดจริงในโปรเจกต์ `Check Out of Range Log` (Plant Log Analyzer) + web tool อื่นๆ ในแบรนด์ A-Class WebCraft

## 📖 Log ความคืบหน้า

### 2026-09-02 — Level 6: Testing & Quality (จากงานจริง ไม่ใช่โจทย์)

วันนี้ติดตั้ง quality gate ทั้ง repo · สรุปสิ่งที่ควรเข้าใจจากงานนี้

**1. "Unit test" กับ "e2e test" ต่างกันตรงไหน — และทำไมต้องมีทั้งคู่**

| | unit (jsdom) | e2e (Playwright) |
|---|---|---|
| รันบนอะไร | จำลอง DOM ด้วย JavaScript ไม่มีเบราว์เซอร์จริง | Chromium ตัวจริง |
| เร็วแค่ไหน | 15 เทสต์ = ~2 วิ | 16 เทสต์ = ~9 วิ |
| ตรวจอะไรได้ | logic · ข้อมูล · เงื่อนไข | สี · ขนาด · การจัดวาง · สิ่งที่ตาเห็น |
| ตรวจอะไร**ไม่ได้** | อะไรก็ตามที่ต้องวาดจริงถึงจะรู้ | — |

jsdom **ไม่มี layout engine** แปลว่ามันไม่รู้ว่าปุ่มกว้างกี่พิกเซล หรือสีที่เห็นจริงคืออะไร
เพราะมันไม่เคย "วาด" หน้าออกมาเลย มันแค่จำลองโครงสร้าง DOM กับพฤติกรรมของ JavaScript
→ กฎอย่าง "contrast ≥4.5:1" หรือ "ปุ่ม ≥44px" จึงต้องใช้เบราว์เซอร์จริงเท่านั้น

**2. บทเรียนที่สำคัญที่สุดของวันนี้ — "เทสต์ที่ผ่านตลอด" อาจไม่ได้ตรวจอะไรเลย**

หนูเขียนเทสต์ว่า *"object store ที่สร้างจริง ต้องตรงกับ `APP_CONFIG.STORES`"* ดูสมเหตุสมผล
แต่พอลองลบ store ออกจาก config เทสต์**ยังผ่าน** — เพราะโค้ดสร้าง store *ตาม config นั้น*
ทั้งสองฝั่งจึงหดตามกันเสมอ เทสต์นี้ตรวจว่า "1 = 1" ไม่ได้ตรวจว่าโปรแกรมถูกหรือผิด

→ **กฎที่ได้:** เขียนเทสต์เสร็จ ต้อง**จงใจทำให้มันแดง**ก่อนเสมอ ถ้าทำให้แดงไม่ได้
แปลว่ามันไม่ได้ตรวจอะไร · ภาษาอังกฤษเรียกหลักการนี้ว่า *"a test that never fails is not a test"*

**3. `var` กับ `const` ต่างกันตรงที่ "ผูกกับ window หรือเปล่า"**

```js
var  A = 1;   // → window.A มีค่า 1  (เข้าถึงจากนอกไฟล์ได้)
const B = 2;  // → window.B เป็น undefined  (แม้ B จะใช้งานได้ในไฟล์ปกติ)
```

นี่คือเหตุผลที่มาตรฐานบังคับให้โมดูลใช้ `var` — ถ้าเปลี่ยนเป็น `const` แอปจะยังทำงาน
ปกติทุกอย่าง แต่เทสต์จะมองไม่เห็นโมดูลทันที เป็นบักที่หาสาเหตุยากมากถ้าไม่รู้มาก่อน

**4. เทสต์เจอบักจริงในโค้ดที่ใช้มาตลอด**

เทสต์ migration เจอว่า `STORAGE_ENGINE.open()` ไม่มี `onblocked` และไม่มี `onversionchange`
→ ถ้าเปิดแอปไว้ 2 แท็บ แล้ว deploy ที่ bump `DB_VERSION` แท็บที่สองจะ**ค้างถาวร**
โดยไม่มี error ให้เห็นเลย · เป็นบักที่อ่านโค้ดเฉยๆ ไม่มีทางเจอ ต้องมีเทสต์ที่จำลอง
"ผู้ใช้คนเดิมเปิดแอปเวอร์ชันใหม่" ถึงจะโผล่

**5. `--no-verify` คืออะไร และทำไมถึงห้าม**

`git commit --no-verify` = ข้าม pre-commit hook · มันมีไว้สำหรับกรณีฉุกเฉินจริงๆ
แต่ถ้า hook ช้าเกิน ~5 วินาที คนจะเริ่มพิมพ์มันเป็นนิสัย แล้ว gate ก็ไร้ความหมาย
→ เหตุผลที่ hook ของเรามีแค่ format + secret + unit test ส่วน e2e ปล่อยให้ CI รัน
**ออกแบบ gate ให้เร็วพอที่จะไม่มีใครอยากข้าม สำคัญกว่าออกแบบให้ครอบคลุมที่สุด**
